# Contributing

## Setup

```bash
git clone https://github.com/Ormorshtein/applicative-load-observability.git
cd applicative-load-observability
uv pip install -e ".[dev]"
pre-commit install
```

## Branching

Branch from `develop`, not `main`. Use descriptive names:

```
feature/scroll-detection
fix/bulk-took-nanoseconds
refactor/shared-latency-tracker
```

Merge to `develop` first. `main` tracks releases.

## Code

- Python 3.11+, enforced by ruff and mypy
- Modules stay under ~300 lines. Split by responsibility when they grow.
- Entry points get clean names (`setup.py`, `stress.py`). Internal modules get a `_`
  prefix (`_client.py`, `_engine.py`).
- Tests go in `tests/unit/<component>/` mirroring the source tree.

### Lint, format, type-check

```bash
ruff check .
ruff format .
mypy analyzer/
```

### Run tests

```bash
pytest                       # all unit tests
pytest tests/unit/analyzer/  # one component
pytest -n auto               # parallel
```

CI (`.github/workflows/ci.yml`) runs ruff check, ruff format --check, mypy, and
`pytest tests/unit/` on every push and PR to `main` / `develop`.

## Docker images

There are **5 images**: `analyzer`, `logstash`, `gateway`, `ch-setup`, `grafana-setup`.
They are built and pushed by `.github/workflows/release.yml` on a `v*` tag push — the
matrix always builds all five, so every release publishes a consistent tag set even when
only one component changed. Do not build and push them by hand.

Build contexts differ per image (matching the release matrix):

| Image | Context | Dockerfile |
|-------|---------|------------|
| `analyzer` | `.` | `analyzer/Dockerfile` |
| `logstash` | `.` | `logstash/Dockerfile` |
| `ch-setup` | `.` | `clickhouse_setup/Dockerfile` |
| `gateway` | `gateway` | `gateway/Dockerfile` |
| `grafana-setup` | `grafana` | `grafana/Dockerfile` |

To build one locally for testing (no push):

```bash
docker build -t alo-analyzer:dev -f analyzer/Dockerfile .
```

## Releasing

1. Update `version` in `pyproject.toml`
2. Update image tags in `docker-compose.yml` (`ch-setup`, `logstash`, `analyzer`,
   `gateway`) and in `helm/alo/values.yaml` (those four plus `grafana-setup`), and bump
   `version` + `appVersion` in `helm/alo/Chart.yaml`
3. Add a section to `CHANGELOG.md` — subsections as relevant: Features, Fixes, Release
4. Commit, push to `develop`, merge to `main`
5. Tag `v<version>` on `main` and push the tag — the release workflow builds and pushes
   all five images

> Keep all four in step — `pyproject.toml`, `docker-compose.yml`, `helm/alo/values.yaml`,
> and `helm/alo/Chart.yaml` (`version` + `appVersion`). They drifted before 2.1.20, when
> `pyproject.toml` was left at `2.1.0` for nineteen releases.

## Dashboards

Dashboards are JSON files under `grafana/provisioning/dashboards/`, generated by the
Python builders in `grafana/`:

```bash
python -c "from grafana._dashboards import export_dashboards; export_dashboards()"
```

This writes **both** `grafana/provisioning/dashboards/*.json` (used by Docker Compose) and
`helm/alo/files/grafana-*.json` (baked into the chart ConfigMap), so the two can't drift.
Commit both. Restart Grafana to pick up changes (`docker compose restart grafana`).

Five dashboards are generated: `alo-main`, `alo-main-he` (Hebrew), `alo-cost-indicators`,
`alo-usage`, `alo-health`. When adding a panel to the main dashboard, add it to the Hebrew
variant too (`grafana/_dashboard_builders.py`, strings in `grafana/_strings.py`).

## ClickHouse schema

`clickhouse_setup/_schema.py` is the single source of truth for the analytics schema and
must stay in sync with the record the analyzer emits
(`analyzer/record_builder/_assembly.py`). When adding a field:

1. Add the key to the assembled record
2. Add the column to `_RAW_COLUMNS`
3. Add it to `_RAW_COLUMN_ADDITIONS` as well, so existing deployments get an
   `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` on upgrade
4. If dashboards will filter on it, consider a bloom-filter skip index
   (`_RAW_INDEX_ADDITIONS`)
5. Extend `tests/unit/clickhouse_setup/test_schema.py`

Changing the materialized view definition triggers a DROP + recreate on upgrade and does
**not** backfill — say so in the changelog when you do it.

## Helm chart

The chart lives in `helm/alo/`. Any change to Docker Compose config, the Logstash
pipeline, the gateway nginx config, or environment variables **must** also update the
corresponding Helm templates.

Key files:
- `helm/alo/templates/logstash/configmap.yaml` — mirrors `logstash/pipeline/observability.conf`
  and `logstash/logstash.yml`
- `helm/alo/templates/gateway/configmap.yaml` — mirrors `gateway/nginx.conf.template`
  (plus optional upstream ES auth injection)
- `helm/alo/templates/gateway/deployment.yaml` — mirrors gateway env vars
- `helm/alo/values.yaml` — default values
- `helm/alo/values.schema.json` — must be updated when adding or removing values

Verify with `helm template test helm/alo/` before committing.

## Project structure

```
analyzer/           FastAPI service (parsing, stress scoring, record building)
gateway/            OpenResty reverse proxy (Lua, fire-and-forget to Logstash)
logstash/           Pipeline config (gateway → analyzer → ClickHouse)
clickhouse_setup/   Schema-as-code + DDL runner (ch-setup image)
grafana/            Dashboard builders, provisioning JSON, datasource setup
prometheus/         Scrape config for the optional monitoring profile
shared/             Shared Python utilities (HTTP client, data generators, stats)
tools/stress/       Load generation tool (11 workload profiles)
tests/unit/         Unit tests (analyzer/, clickhouse_setup/, grafana/, challenges/, shared/)
tests/integration/  Gateway resilience + Grafana dashboard verification
tests/challenges/   Interactive challenge scenarios (14 total)
helm/alo/           Kubernetes Helm chart
docs/               Architecture, Helm guide, product spec
```
